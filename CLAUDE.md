# P-Flow : notes pour les sessions de développement

- Appli vanilla JS + Vite (`index.html`, `src/main.js`, `src/style.css`, `src/firebase.js`), empaquetée pour Android avec Capacitor 7 (`android/`).
- Langue de l'interface : français, tutoiement. Ton simple : l'appli est aussi utilisée par des personnes peu à l'aise avec l'informatique.
- **Textes courts (exigence du propriétaire, 28/10/2026)** : peu d'écrit, lisible d'un coup d'œil. Chaque phrase est raccourcie au plus court sans perdre d'information utile (ex. pas « Fin octobre : combien as-tu sur ton compte ? » mais « Ton solde ? »). Vaut pour tout nouveau texte : fenêtres, Réglages, bulles, messages, didacticiel.
- **Aucune donnée personnelle dans le dépôt** (dépôt public) : pas de montants réels, d'emails ou de noms dans le code, les tests ou les exemples.
- Données Firestore : `users/{uid}/meta/settings` (`pro`, `taux`, `periodicite` ; facultatifs depuis le patch 1 : `couleurs` = `{ brut, urssaf, net, dep, reste }` en `#rrggbb` ou `null` pour la couleur par défaut (patch 3 : + `autres`, `fixes`, `ep`, clés facultatives ignorées par les versions d'avant ; une couleur prise par une autre ligne ou trop proche, écart « redmean » < 60, est bloquée à l'écran), `sauvegarde` = `{ drive, frequence, derniere }`, `dataVersion`), `users/{uid}/entries/{id}` (opérations ponctuelles, champ `month` = `AAAA-MM`), `users/{uid}/recurring/{id}` (fixes mensuels, `start`/`end` = `AAAA-MM`). Depuis le patch 2 : réglages facultatifs `epargne` (`true` suivie, `false` refusée, absent = pas encore choisi) et `accent` (couleur d'accentuation : `bleu` par défaut, `violet`, `rose`, `rouge`, `orange`, `ambre`, `vert`, `turquoise`, `graphite` ; teintes dans `style.css`, `:root[data-accent=…]`) ; `users/{uid}/periodiques/{id}` (fixes trimestriels / annuels et versements d'épargne automatiques : `type` = `depense` | `revenu` | `epargne`, `label`, `amount`, `urssaf`, `freq` = `mois` | `trimestre` | `annee`, `start`, `end`, `createdAt`) ; `users/{uid}/epargne/{id}` (`op` = `depot` | `retrait` | `solde`, `label` = nom du compte, `amount`, `date`, `month`, `createdAt` ; ne jamais nommer un champ `kind`, retiré par `plain()`). Accès : `allowlist/{email}` (personnes autorisées, gérées par l'administrateur dans Réglages) et `admins/{uid}` (créé à la main dans la console Firebase) ; `demandes/{email}` (patch 2 : demande d'accès, champs `uid`, `message`, `nom`, `at`). Patch 3 (rangées à part, jamais dans `entries` ni `recurring`) : `users/{uid}/jours/{id du fixe}` (`jour` 1 à 31, `createdAt` : jour où tombe un fixe de `recurring` ou `periodiques` ; absent = le 1er ; 29-31 → dernier jour des mois plus courts) ; `users/{uid}/soldes/{id}` (`montant` signé, `date` `AAAA-MM-JJ`, `createdAt` : solde du compte courant, historique jamais effacé, le plus récent par `date` puis `createdAt` fait foi) ; `users/{uid}/pointages/{id de l'opération}` (`passee` booléen, `createdAt` : réponse à « Déjà passée sur ton compte ? » pour une opération de `entries` ou `epargne` datée avant ou le jour du dernier solde ; `false` = comptée aujourd'hui dans le solde prévu). Patch 4 : `users/{uid}/urssaf/{période}` (période = `AAAA-MM` en déclaration mensuelle, `AAAA-T1`…`AAAA-T4` en trimestrielle ; `payee` booléen, `date` `AAAA-MM-JJ` et `montant` quand `payee` = true, `createdAt` : paiement réel de l'URSSAF, il remplace l'estimation partout ; `payee: false` = « pas encore », comptée dans le solde prévu dès aujourd'hui ; écrit avec `merge`) ; réglages facultatifs `objectif` (montant à garder sur le compte à la fin de chaque mois, `null` = aucun) et `objectifs` (`{ 'AAAA-MM': montant }` pour un mois réglé à part, `null` = reprend celui de tous les mois). Couvertes par la règle `users/{uid}/{document=**}` : rien à changer dans `firestore.rules`. Règles dans `firestore.rules` (à recopier dans la console Firebase à chaque changement).
- **Règle du propriétaire : ne jamais publier ni compiler de version (APK, test ou release) sans son accord explicite.** Avant chaque publication, lui demander s'il faut recompiler et quel numéro donner. Format souhaité : `0.1.N-beta` (affiché « 0.1.N bêta »). La série repart de `0.1.0-beta` (publiée le 21/10/2026) ; `0.1.1-beta` = patch 1 (publiée le 21/10/2026) ; `0.1.2-beta` = patch 2 (publiée le 23/10/2026) ; `0.1.3-beta` = patch 3 (publiée le 24/10/2026) ; `0.1.4-beta` = patch 4 (publiée le 25/10/2026) ; `0.1.5-beta` = patch 5 (publiée le 26/10/2026) ; prochaines versions 0.1.6, 0.1.7… Les anciennes 0.1.7 à 0.1.12 étaient des tests internes.
- Mécanique : la version publiée est celle de `package.json`. Un push sur main ne publie que si le tag `v<version>` n'existe pas encore ; on ne change donc `version` dans `package.json` qu'après accord, avec le numéro choisi. Sans changement de version, le push vérifie seulement le build web (rien n'est publié). Les APK de test se font par lancement manuel du workflow, aussi après accord. Le versionCode Android = `github.run_number` (toujours croissant).
- **Notes de version obligatoires** (souhait du propriétaire) : avant chaque publication, écrire `notes-de-version/<version>.md`, en français simple. Le workflow s'en sert comme description de la version sur GitHub et refuse de publier sans ce fichier ; l'appli l'affiche une fois après la mise à jour (« Nouveautés »). **Format court exigé par le propriétaire (25/10/2026, toutes les notes réécrites ainsi)** : les gens ne lisent pas les longues notes, donc l'essentiel en premier et beaucoup plus court (~120 mots, une ligne par point, aucun détail technique) :
  - `## P-Flow <version> : patch N` (titre, caché dans l'appli) ;
  - `### L'essentiel` : 2 à 4 nouveautés qui changent l'usage, chacune `**Nom** : une phrase` ;
  - `### Aussi dans cette version` : 5 lignes au plus, regroupées (le look en une ligne, « petites corrections » en une ligne) ;
  - `### Installer` : une ligne Android / PC et iPhone, plus « Rien n'est effacé : mets à jour tous tes appareils. » quand des données nouvelles sont rangées à part.
- APK publiée sous le nom `P-Flow-<version>.apk` ; lien de partage stable : `https://lorn-noross.github.io/P-Flow/telecharger.html` (lit `version.json`).
- La clé de signature `android/app/p-flow-release.p12` est protégée par le secret GitHub `ANDROID_KEYSTORE_PASSWORD`. Ne jamais la régénérer : sinon les mises à jour ne s'installent plus par-dessus l'ancienne version.
- Vérifier `npm run build` avant chaque push. Le build Android ne tourne que dans GitHub Actions.
- Réglages propres à chaque appareil (`localStorage`) : `pf-showFixed`, `pf-maj-auto` (vérification des mises à jour : `ouverture`, `jour`, `semaine`, `jamais`), `pf-maj-last`, `pf-allowed-<uid>`, `pf-admin-<uid>` ; patch 2 : `pf-theme` (`auto`, `clair`, `sombre`), `pf-noir` (`1`), `pf-texte` (`grand`), `pf-effets` (`reduits` ; absent = réduits d'office si `navigator.deviceMemory` ≤ 2), `pf-groupe` (dépenses regroupées), `pf-nouveautes` (version dont les nouveautés ont été vues), `pf-accent` (copie locale de la couleur d'accentuation du compte, appliquée avant la synchronisation) ; patch 3 : `pf-showFixedRev` (revenus fixes dépliés dans l'écran Mois), `pf-vue-compte` (`0` = gros chiffre « Reste du mois » même avec un solde noté ; absent ou `1` = « Prévu sur ton compte ») ; patch 4 : `pf-urs-plus-tard` (`AAAA-MM-JJ|période,période…` : « URSSAF payée ? » mise de côté ce jour-là après « Pas encore », une ou plusieurs périodes ; vidée quand un nouveau solde est noté, pour reposer la question), `pf-offre-ep` (`AAAA-MM-JJ|n` : première fois que l'offre d'épargne a été vue, nombre d'ouvertures ; plus de « Nouveau » après 30 jours, rangée après 8 ouvertures), `pf-maj-auto` accepte aussi `mois` (30 jours). L'apparence est appliquée avant le premier affichage par le petit script de `index.html` (même logique que `applyAppearance()`).
- Module natif maison `PFlowNative` (`android/app/src/main/java/…/PFlowNativePlugin.java`, déclaré dans `MainActivity`) : autorisation Google Drive (`drive.file`, Identity AuthorizationClient, sans fenêtre si déjà accordée), « Enregistrer sous », téléchargement et installation des mises à jour (uniquement depuis `github.com/Lorn-noross/P-Flow/releases/download/`, paquet vérifié avant installation), `setSystemBars` (patch 2 : fond de la fenêtre et icônes du système assortis au thème choisi ; renvoie `top`, la hauteur de la barre d'état sur Android 15+).
- Sauvegardes (`src/drive.js` + section « sauvegardes » de `main.js`) : une sauvegarde = tout le compte en JSON (`app: 'P-Flow'`, `format`, `dataVersion` ; `format: 2` depuis le patch 2 avec `periodiques` et `epargne` ; `format: 3` depuis le patch 3 avec `jours`, `soldes` et `pointages`, ignorés sans dégât par les versions d'avant ; `format: 4` depuis le patch 4 avec `urssaf` ; les fichiers `format: 1` à `3` se restaurent toujours). Restaurer remet seulement les documents absents (par identifiant) : jamais d'écrasement ni de suppression, réglages non modifiés. Drive : dossier « P-Flow Sauvegardes », 12 copies gardées, les plus anciennes vont à la corbeille. Navigateur : la fenêtre Google exige un clic, donc `Drive.getToken` est appelé avant tout `await` dans les gestionnaires de clic.
- Projet Google Cloud = projet Firebase `p-flow-a56b0` (écran de consentement « En production », champ d'accès `drive.file`, origine `https://lorn-noross.github.io` autorisée sur le client Web).
- Clavier : sur Android 15+ (bord à bord), le clavier recouvre la WebView sans la redimensionner. Sa hauteur arrive par `@capacitor/keyboard` (et `visualViewport` dans les navigateurs) dans la variable CSS `--kb` ; la fenêtre d'ajout se cale au-dessus. Ne pas redimensionner la WebView en natif (Chromium peut alors refermer le clavier). `adjustResize` est déclaré dans le manifeste.
- Haut de l'écran (patch 2) : pas de barre opaque, le titre et le nuage flottent dans des pilules en verre (`.pill`) et le fond monte jusqu'en haut. Sur Android 15+, `MainActivity.immersiveTop()` remplace les marges de Capacitor (`adjustMarginsForEdgeToEdge: auto`, gardé comme filet de sécurité) : marges à gauche, à droite et en bas, mais la page passe sous la barre d'état ; sa hauteur arrive dans la variable CSS `--sat` (par défaut `env(safe-area-inset-top)`, faux dans les WebView < 140). Tout espace en haut de l'écran utilise `var(--sat)`, jamais `env(safe-area-inset-top)` directement. Avant Android 15 : barre d'état colorée, comme avant.

## Règle n°1 : ne jamais perdre ni abîmer les données (exigence absolue du propriétaire)
Des personnes (dont la famille du propriétaire) ont de vraies données dans l'appli. Une mise à jour ne doit **jamais** les effacer, les déplacer ni les rendre illisibles. Cette règle passe avant toute nouveauté.
- **On ajoute, on ne retire jamais.** Ne jamais renommer, déplacer ni supprimer une collection ou un chemin Firestore (`users/{uid}/…`), un champ existant, ni une clé `localStorage` (`pf-…`). Ne jamais restreindre `firestore.rules` sur un chemin existant.
- **Tout nouveau champ est facultatif** : le code doit marcher quand il est absent (valeur par défaut), puisque les données existantes ne l'ont pas.
- **Plusieurs versions tournent en même temps** (un téléphone pas encore mis à jour, le PC déjà à jour, sur le même compte) :
  - une ancienne version doit continuer à lire ce qu'écrit la nouvelle ;
  - une écriture ne doit jamais effacer un champ qu'elle ne connaît pas : `setDoc(…, { merge: true })` pour les réglages ; pour réécrire un document entier, repartir du document lu (`plain(o)`) puis modifier ;
  - les versions jusqu'à 0.1.0-beta réécrivent une opération modifiée (`entries`) sans garder les champs inconnus : tant qu'elles circulent, ne rien mettre d'indispensable dans un nouveau champ d'opération.
  - les versions jusqu'à 0.1.1-beta comptent tout fixe de `recurring` chaque mois, traitent tout type inconnu comme une dépense et le transforment en `depense` si on le modifie : **ne rien mettre de nouveau dans `entries` ni `recurring`** (c'est pourquoi l'épargne et les fixes non mensuels sont dans `epargne` et `periodiques`). Écritures liées (arrêter un fixe et créer son remplaçant) : toujours ensemble avec `writeBatch`, jamais de suppression.
- **Version des données** : `DATA_VERSION` dans `src/main.js` ; champ `dataVersion` dans `users/{uid}/meta/settings` (absent = 1). Une appli qui voit un `dataVersion` plus grand que le sien passe en lecture seule et demande la mise à jour (garde-fou présent depuis le patch 1). Si une donnée doit vraiment changer de forme :
  1. demander l'accord du propriétaire ;
  2. sauvegarde complète du compte avant toute conversion ;
  3. conversion idempotente (relançable sans dégât), étape par étape (1→2, puis 2→3…), en gardant l'ancienne forme lisible tant que des versions qui l'utilisent circulent ;
  4. écrire `dataVersion` seulement après une conversion réussie.
- **Test de non-régression des données avant chaque publication** (voir `tests/README.md`) : des jeux de données fictifs au format de chaque ancienne version sont chargés dans l'appli, construite avec un faux Firebase en mémoire (`tests/fakes/`) ; on vérifie que tout s'affiche à l'identique et que modifier ou supprimer ne fait rien perdre d'autre. Quand le format évolue, on ajoute un nouveau jeu de données sans retirer les anciens.

## Qualité avant chaque publication (exigence du propriétaire)
1. Relire intégralement chaque modification (diff complet), puis lancer le plugin Code Review sur les changements.
2. Vérifier les API utilisées dans la documentation officielle à jour (Firebase, Capacitor, plugins) : pas de mémoire approximative.
3. `npm run build` sans erreur ni avertissement nouveau.
4. Tester l'interface en local (Playwright) : téléphone et PC, thème clair et sombre, parcours ajout / modification / suppression. Lancer le test de non-régression des données et le test de fluidité (`tests/README.md`). **Deux niveaux** (26/10/2026) : APK de test = `node tests/run.mjs --rapide` (dernier jeu de données, téléphone clair et PC sombre) ; publication = test complet (tous les jeux, tous les écrans) et test de fluidité, obligatoires.
   - Animations : mouvements uniquement en `transform` / `opacity` (Web Animations API, fonction `anim()`), courts fondus de couleur tolérés, coupées par « Effets réduits » et `prefers-reduced-motion` ; flou seulement sur les pilules (barre du bas, pilules du haut) et les fenêtres maison en verre (`.pop` : calendriers, listes de choix, teinte ; bulle du graphique `.bubble` ; message `.toast` ; demande du 23/10/2026, validé à l'APK 60 : `.pop` et `.bubble` en verre discret, fond `--pop-glass` à ~80 % d'opacité, `blur(20px) saturate(1.25)`, reflet d'accent 7 % ; `.toast` avec le verre des pilules, `--glass`, `blur(18px) saturate(1.6)`), coupé par « Effets réduits » ; effets de survol seulement sous `@media (hover:hover)` (au doigt, le survol reste collé) ; pas de calcul de mise en page forcé pendant une transition.
   - **Homogénéité (exigence absolue du propriétaire, 24/10/2026)** : toute nouveauté (fenêtre, carte, menu, bouton, bulle…) doit ressembler « comme deux gouttes d'eau » au thème existant. Réutiliser les classes et les jetons déjà là (`.card`, `.pill`, `.seg`, `.btn`, `.row`, `--glass`, `--surface`, `--card`, rayons, ombres, flou des pilules) ; aucun effet propre en plus (reflet coloré, liseré, dégradé, flou ou saturation différents, autre opacité). En cas de doute, copier l'élément existant le plus proche. Vérifier à l'écran à côté de l'existant (clair, sombre, noir absolu) avant toute APK de test. C'est une règle pour tout ce qui sera créé ensuite, pas une demande de retoucher ce qui existe.
   - **Animations toujours fluides et toujours les mêmes (exigence absolue du propriétaire, 26/10/2026)** : toute nouvelle interface respecte le thème de l'appli ET ses animations. Jamais une animation différente selon l'endroit pour un même geste, jamais un changement sec. Réutiliser seulement les animations existantes, avec leurs durées et courbes (`EASE`, `SPRING`, `anim()` dans `main.js` et `pickers.js`) :
     - choix dans un `.seg` (interrupteur, boutons à choix) : rebond du bouton choisi (écouteur global) ; **garder le même élément** d'un rendu à l'autre (ne jamais le recréer, sinon la transition ne se joue pas : exemple `#hero-mode` dans Mois, `#y-mode` dans Année) ;
     - changement de vue (bascule « Sur mon compte / Reste », changement de mois ou d'écran) : jamais tout redessiner d'un coup ; montant qui défile (`rollNumber`, même clé), barres qui repoussent (`growBars`), contenu en glissement (`slideIn`) ou en fondu court (opacité, `EASE`, ~320 ms) ;
     - carte, bloc ou ligne qui apparaît : `riseIn` (une carte) ou `cascadeIn` (une liste) ;
     - fenêtre, menu, calendrier, liste de choix, bulle : `openPop` / `openChoice` / `openCalendar` de `pickers.js` (ressort depuis l'élément touché) ; feuille du bas : `openSheet` ; message : `toast` / `toastUndo` ;
     - tout est coupé par « Effets réduits » et `prefers-reduced-motion` (`motionOK()`), en `transform` / `opacity` seulement.
     En cas de doute, copier l'animation de l'élément existant le plus proche. Avant chaque APK de test : faire chaque nouveau geste à l'écran à côté de son équivalent existant et vérifier que l'animation est la même ; un test qui vérifie que l'élément n'est pas recréé quand c'est le cas (comme `Patch5Annee`).
   - **Sous-interfaces aux couleurs de l'appli** (demande du propriétaire, 23/10/2026) : aucune fenêtre native du système à l'intérieur de l'appli (liste `<select>`, sélecteur de date, sélecteur de couleur, `alert` / `confirm` / `prompt`). Tout menu, liste de choix, calendrier, sélecteur ou confirmation est fait maison, en verre, aux couleurs du thème (clair, sombre, noir absolu) et de la couleur d'accentuation. Seules exceptions, impossibles à habiller : le sélecteur de fichiers du système (« Importer une sauvegarde », import Excel), « Enregistrer sous », la fenêtre Google de connexion / Drive et celle d'installation d'Android. À chaque patch : `grep` (`<select`, `type="date"`, `type="month"`, `type="color"`, `confirm(`, `alert(`) puis vérification à l'écran dans les deux thèmes.
   - Nouveautés : `notes-de-version/<version>.md` est intégré à la construction (`latestNotes()` dans `vite.config.js` : version publiée si elle existe, sinon les notes les plus récentes pour les APK de test). Ne pas laisser de brouillon d'une version suivante au moment de publier.
5. Si le modèle de données change : mettre à jour `firestore.rules` et prévenir le propriétaire qu'il doit les recopier dans la console.
6. Poids : budget actuel JS ≈ 205 Ko gzip depuis le patch 4 (199 Ko au patch 3, 185 Ko au patch 2 ; dont ~140 Ko Firebase), CSS ≈ 12,5 Ko gzip, une seule police (Figtree variable, ~20 Ko + latin étendu), APK ≈ 5 Mo. Ne pas ajouter de bibliothèque lourde ; préférer le code natif du navigateur ; charger à la demande ce qui n'est pas nécessaire au démarrage.
7. Donner au propriétaire la liste des changements, le numéro de version proposé, et attendre son accord avant de monter la version.
8. **Économie (demande du propriétaire, 26/10/2026)** : chaque session consomme sa limite d'utilisation, donc aller droit au but.
   - Regrouper les retours en attente dans une seule APK de test ; tests rapides pour une APK de test, complets seulement avant la publication.
   - Pas de captures d'écran, de maquettes ni de scripts de diagnostic sans nécessité ; lire les fichiers par morceaux ciblés ; filtrer les sorties de commande (seulement les échecs et le total).
   - À la publication d'une version, déplacer son détail de ce fichier vers `docs/historique-patchs.md` (ce fichier est relu à chaque session : le garder court).
   - Conseiller au propriétaire d'ouvrir une nouvelle conversation à chaque nouveau patch (une longue conversation coûte plus cher à chaque message).

1 bis. **Relevé de banque** (idée du propriétaire du 25/10/2026, jugée « très maline » ; à la place d'une connexion bancaire, voir « Plus tard ») : fichier CSV (ou OFX / QIF quand la banque le propose, plus fiable, avec le solde) téléchargé depuis l'espace en ligne de la banque (ex. BoursoBank : CSV, OFX, QIF). Formats à gérer : séparateur `;`, montants à virgule, débit / crédit séparés ou montant signé, lignes d'en-tête en trop, libellés de banque (« PRLV SEPA EDF … », « CB CARREFOUR 12/10 »). Demander au propriétaire (et à ses parents) un relevé de leur banque, données masquées ; jamais dans le dépôt.
   - **Souhait du propriétaire** : le relevé est relié à « Sur mon compte » et ne doit pas fausser le reste du mois. Choix retenu à lui expliquer (25/10/2026) : pas deux listes séparées (le reste du mois deviendrait faux et les deux vues se contrediraient) ; le vrai risque est de **compter deux fois** (loyer du relevé + fixe Loyer, prélèvement URSSAF + URSSAF estimée, virement vers le Livret A + épargne). Donc l'import **rapproche** chaque ligne de ce qui existe déjà avant d'ajouter quoi que ce soit.
   - Étapes de l'assistant : (1) **solde du compte** : le dernier solde du relevé (ou calculé) est noté à la date du relevé (`soldes`) ; tout ce qui est daté avant est « déjà passé » (`pointages`), la prévision « Sur mon compte » repart de là ; (2) **reconnu automatiquement** : lignes qui correspondent à une opération ou un fixe déjà noté (même montant, date à ±3 jours, libellé proche) = rien d'ajouté, seulement pointées ; prélèvement URSSAF = « URSSAF de <mois> payée » avec le montant réel (`urssaf`) ; virement vers un compte d'épargne connu = dépôt d'épargne ; (3) **fixes détectés** : même libellé nettoyé et même montant (à ~1 € près) au moins 2 à 3 mois de suite → liste à cocher « Ajouter comme fixe » avec le jour (s'il n'existe pas déjà) ; (4) **opérations ponctuelles** restantes : liste à cocher (tout cocher / rien), type deviné (débit = dépense, crédit = revenu, « soumis à l'URSSAF » à confirmer pour un crédit), libellé nettoyé et modifiable ; (5) résumé et « Annuler cet import ».
   - Identifiants fixes calculés à partir de la ligne (date, montant, libellé) : réimporter le même relevé ne crée aucun doublon. Seulement les collections existantes (`entries`, `recurring` / `periodiques` + `jours`, `epargne`, `urssaf`, `soldes`, `pointages`) ; liste des documents créés gardée à part pour « Annuler ». Sauvegarde avant import.

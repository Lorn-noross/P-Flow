# P-Flow : notes pour les sessions de développement

- Appli vanilla JS + Vite (`index.html`, `src/main.js`, `src/style.css`, `src/firebase.js`), empaquetée pour Android avec Capacitor 7 (`android/`).
- Langue de l'interface : français, tutoiement. Ton simple : l'appli est aussi utilisée par des personnes peu à l'aise avec l'informatique.
- **Aucune donnée personnelle dans le dépôt** (dépôt public) : pas de montants réels, d'emails ou de noms dans le code, les tests ou les exemples.
- Données Firestore : `users/{uid}/meta/settings` (`pro`, `taux`, `periodicite` ; facultatifs depuis le patch 1 : `couleurs` = `{ brut, urssaf, net, dep, reste }` en `#rrggbb` ou `null` pour la couleur par défaut, `sauvegarde` = `{ drive, frequence, derniere }`, `dataVersion`), `users/{uid}/entries/{id}` (opérations ponctuelles, champ `month` = `AAAA-MM`), `users/{uid}/recurring/{id}` (fixes, `start`/`end` = `AAAA-MM`). Accès : `allowlist/{email}` (personnes autorisées, gérées par l'administrateur dans Réglages) et `admins/{uid}` (créé à la main dans la console Firebase). Règles dans `firestore.rules` (à recopier dans la console Firebase à chaque changement).
- **Règle du propriétaire : ne jamais publier ni compiler de version (APK, test ou release) sans son accord explicite.** Avant chaque publication, lui demander s'il faut recompiler et quel numéro donner. Format souhaité : `0.1.N-beta` (affiché « 0.1.N bêta »). La série repart de `0.1.0-beta` (publiée le 21/10/2026) ; `0.1.1-beta` = patch 1 (publiée le 21/10/2026) ; prochaines versions 0.1.2, 0.1.3… Les anciennes 0.1.7 à 0.1.12 étaient des tests internes.
- Mécanique : la version publiée est celle de `package.json`. Un push sur main ne publie que si le tag `v<version>` n'existe pas encore ; on ne change donc `version` dans `package.json` qu'après accord, avec le numéro choisi. Sans changement de version, le push vérifie seulement le build web (rien n'est publié). Les APK de test se font par lancement manuel du workflow, aussi après accord. Le versionCode Android = `github.run_number` (toujours croissant).
- **Notes de version obligatoires** (souhait du propriétaire) : avant chaque publication, écrire `notes-de-version/<version>.md` (nouveautés, améliorations, sécurité des données, installation ; en français simple). Le workflow s'en sert comme description de la version sur GitHub et refuse de publier sans ce fichier.
- APK publiée sous le nom `P-Flow-<version>.apk` ; lien de partage stable : `https://lorn-noross.github.io/P-Flow/telecharger.html` (lit `version.json`).
- La clé de signature `android/app/p-flow-release.p12` est protégée par le secret GitHub `ANDROID_KEYSTORE_PASSWORD`. Ne jamais la régénérer : sinon les mises à jour ne s'installent plus par-dessus l'ancienne version.
- Vérifier `npm run build` avant chaque push. Le build Android ne tourne que dans GitHub Actions.
- Réglages propres à chaque appareil (`localStorage`) : `pf-showFixed`, `pf-maj-auto` (vérification des mises à jour : `ouverture`, `jour`, `semaine`, `jamais`), `pf-maj-last`, `pf-allowed-<uid>`, `pf-admin-<uid>`.
- Module natif maison `PFlowNative` (`android/app/src/main/java/…/PFlowNativePlugin.java`, déclaré dans `MainActivity`) : autorisation Google Drive (`drive.file`, Identity AuthorizationClient, sans fenêtre si déjà accordée), « Enregistrer sous », téléchargement et installation des mises à jour (uniquement depuis `github.com/Lorn-noross/P-Flow/releases/download/`, paquet vérifié avant installation).
- Sauvegardes (`src/drive.js` + section « sauvegardes » de `main.js`) : une sauvegarde = tout le compte en JSON (`app: 'P-Flow'`, `format`, `dataVersion`). Restaurer remet seulement les documents absents (par identifiant) : jamais d'écrasement ni de suppression, réglages non modifiés. Drive : dossier « P-Flow Sauvegardes », 12 copies gardées, les plus anciennes vont à la corbeille. Navigateur : la fenêtre Google exige un clic, donc `Drive.getToken` est appelé avant tout `await` dans les gestionnaires de clic.
- Projet Google Cloud = projet Firebase `p-flow-a56b0` (écran de consentement « En production », champ d'accès `drive.file`, origine `https://lorn-noross.github.io` autorisée sur le client Web).
- Clavier : sur Android 15+ (bord à bord), le clavier recouvre la WebView sans la redimensionner. Sa hauteur arrive par `@capacitor/keyboard` (et `visualViewport` dans les navigateurs) dans la variable CSS `--kb` ; la fenêtre d'ajout se cale au-dessus. Ne pas redimensionner la WebView en natif (Chromium peut alors refermer le clavier). `adjustResize` est déclaré dans le manifeste.

## Règle n°1 : ne jamais perdre ni abîmer les données (exigence absolue du propriétaire)
Des personnes (dont la famille du propriétaire) ont de vraies données dans l'appli. Une mise à jour ne doit **jamais** les effacer, les déplacer ni les rendre illisibles. Cette règle passe avant toute nouveauté.
- **On ajoute, on ne retire jamais.** Ne jamais renommer, déplacer ni supprimer une collection ou un chemin Firestore (`users/{uid}/…`), un champ existant, ni une clé `localStorage` (`pf-…`). Ne jamais restreindre `firestore.rules` sur un chemin existant.
- **Tout nouveau champ est facultatif** : le code doit marcher quand il est absent (valeur par défaut), puisque les données existantes ne l'ont pas.
- **Plusieurs versions tournent en même temps** (un téléphone pas encore mis à jour, le PC déjà à jour, sur le même compte) :
  - une ancienne version doit continuer à lire ce qu'écrit la nouvelle ;
  - une écriture ne doit jamais effacer un champ qu'elle ne connaît pas : `setDoc(…, { merge: true })` pour les réglages ; pour réécrire un document entier, repartir du document lu (`plain(o)`) puis modifier ;
  - les versions jusqu'à 0.1.0-beta réécrivent une opération modifiée (`entries`) sans garder les champs inconnus : tant qu'elles circulent, ne rien mettre d'indispensable dans un nouveau champ d'opération.
- **Version des données** : `DATA_VERSION` dans `src/main.js` ; champ `dataVersion` dans `users/{uid}/meta/settings` (absent = 1). Une appli qui voit un `dataVersion` plus grand que le sien passe en lecture seule et demande la mise à jour (garde-fou présent depuis le patch 1). Si une donnée doit vraiment changer de forme :
  1. demander l'accord du propriétaire ;
  2. sauvegarde complète du compte avant toute conversion ;
  3. conversion idempotente (relançable sans dégât), étape par étape (1→2, puis 2→3…), en gardant l'ancienne forme lisible tant que des versions qui l'utilisent circulent ;
  4. écrire `dataVersion` seulement après une conversion réussie.
- **Test de non-régression des données avant chaque publication** (voir `tests/README.md`) : des jeux de données fictifs au format de chaque ancienne version sont chargés dans l'appli, construite avec un faux Firebase en mémoire (`tests/fakes/`) ; on vérifie que tout s'affiche à l'identique et que modifier ou supprimer ne fait rien perdre d'autre. Quand le format évolue, on ajoute un nouveau jeu de données sans retirer les anciens.

## Qualité avant chaque publication (exigence du propriétaire)
1. Relire intégralement chaque modification (diff complet), puis lancer le plugin Code Review sur les changements.
2. Vérifier les API utilisées dans la documentation officielle à jour (Firebase, Capacitor, plugins) : pas de mémoire approximative.
3. `npm run build` sans erreur ni avertissement nouveau.
4. Tester l'interface en local (Playwright) : téléphone et PC, thème clair et sombre, parcours ajout / modification / suppression. Lancer le test de non-régression des données (`tests/README.md`).
5. Si le modèle de données change : mettre à jour `firestore.rules` et prévenir le propriétaire qu'il doit les recopier dans la console.
6. Poids : budget actuel JS ≈ 167 Ko gzip depuis le patch 1 (dont ~140 Ko Firebase), CSS ≈ 6 Ko gzip, APK ≈ 5 Mo. Ne pas ajouter de bibliothèque lourde ; préférer le code natif du navigateur ; charger à la demande ce qui n'est pas nécessaire au démarrage.
7. Donner au propriétaire la liste des changements, le numéro de version proposé, et attendre son accord avant de monter la version.

- **Nouveautés après une mise à jour** : à la première ouverture d'une nouvelle version, afficher les nouveautés de cette version (contenu de `notes-de-version/<version>.md`, intégré à la construction), une seule fois par appareil (nouvelle clé `localStorage`). Les nouveautés restent consultables dans **Réglages**, sous le numéro de version : lien **« À propos de cette mise à jour »**.

Le thème suit déjà le système ; la CSS prévoit `data-theme="light|dark"` sur `<html>`, ce qui permettrait aussi un choix Automatique / Clair / Sombre. **Décidé : réglage propre à chaque appareil** (nouvelle clé `localStorage`), car il dépend de l'écran (noir absolu sur un téléphone OLED, pas forcément sur le PC).
- **Nouvelle icône** (faite par une graphiste) : à partir de la source vectorielle ou des PNG 1024 px (premier plan transparent, fond, version complète, version monochrome), générer les icônes Android adaptatives (avec couche `monochrome` pour les icônes à thème), les icônes web (`icon-192.png`, `icon-512.png`, `icon-maskable-512.png`, `icon.svg`), `apple-touch-icon.png` (180 px, opaque) et l'écran de démarrage. **Exigence du propriétaire : remplacer l'icône partout, APK ET version web** : icônes Android (`android/app/src/main/res/mipmap-*`, `drawable*/splash.png`, couleur de fond), `public/` (`icon.svg` = onglet du navigateur, `icon-192/512`, `icon-maskable-512`, `apple-touch-icon.png` = écran d'accueil iPhone, `manifest.webmanifest`), page `public/telecharger.html` (affiche `icon-192.png`), et le logo dans l'appli (symbole `#i-wave` de `index.html` : connexion, barre latérale) si le nouveau dessin doit aussi le remplacer. Attention : `public/sw.js` garde `icon.svg` et `apple-touch-icon.png` en cache, donc monter `CACHE` (`pflow-v2` → `pflow-v3`) sinon la version web garde l'ancienne icône ; sur iPhone, l'icône de l'écran d'accueil ne change qu'en rajoutant l'appli sur l'écran d'accueil (à dire au propriétaire).
- **Mode épargne** (demandé par le père du propriétaire). Choix validés par le propriétaire :
  - **L'épargne baisse le reste** : Reste = net − dépenses − épargne (dépôts − retraits).
  - **Comptes nommés librement** (Livret A, PEL…, comme les libellés, avec suggestions) et un **total général**.
  - Bouton **+** → type « Épargne » avec trois choix : **J'ai mis de côté** (dépôt), **J'ai repris** (retrait, redonne de l'argent au reste du mois), **J'ai actuellement** (solde du compte à une date).
  - Solde d'un compte = dernier « J'ai actuellement » + dépôts − retraits notés depuis.
  - **Fixes** : module « Épargne » pour un versement automatique chaque mois (ou trimestre / année).
  - **Année** : colonne « Épargne » entre « Dépenses » et « Reste » (tableau, totaux), et ligne dans la légende du mois.
- **Fixes trimestriels et annuels** (demandé par la sœur du propriétaire) : « Revient chaque mois » devient un choix **chaque mois / chaque trimestre / chaque année**, pour les dépenses, les revenus et l'épargne. **Choix validé : compté en entier le mois où il tombe** (comme sur le compte en banque), à partir du mois de départ choisi (annuel à partir de mars = chaque mars ; trimestriel = mars, juin, sept., déc.), avec la prochaine échéance affichée dans Fixes.
- **Compatibilité (règle n°1) pour l'épargne et les fixes non mensuels** : les versions jusqu'à 0.1.1 comptent tout fixe de `recurring` chaque mois, traitent tout type inconnu comme une dépense, et le transforment en `depense` si on le modifie. Donc **ne rien mettre de nouveau dans `entries` ni `recurring`** : nouvelles collections sous `users/{uid}/` (par ex. `epargne` pour dépôts / retraits / soldes, `periodiques` pour les fixes trimestriels / annuels et l'épargne fixe), déjà couvertes par `firestore.rules` (`users/{uid}/{document=**}`), donc rien à recopier dans la console. Les anciennes versions ne les voient pas (rien de faux ni d'abîmé, il faut juste mettre à jour). Sauvegardes : inclure les nouvelles collections (`format: 2`), et toujours restaurer les sauvegardes `format: 1`. Ajouter un jeu de données de test au nouveau format, sans retirer les anciens.
